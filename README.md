# Дебиторка 1С для Битрикс24

Локальное приложение Битрикс24, которое показывает счета, оплаты и дебиторку из **1С Фреш** (Бухгалтерия для Казахстана) и позволяет выставить счёт прямо из сделки. Сделано для ТОО «Мой арбитр» и ТОО «АрбитрЪ» (портал `myarbitr.bitrix24.kz`), но легко адаптируется под другие компании на 1С Фреш.

## Что умеет

**Отчёт (левое меню Битрикса, пункт «Дебиторка 1С»)**
- Две компании и переключатель «Мой арбитр / АрбитрЪ / Обе». Каждая компания это отдельная база 1С.
- Выставлено счетов, начислено, оплачено, дебиторка, просрочка, авансы за выбранный период.
- Структура долга по возрасту: в сроке, 1–30, 31–60, 61–90, 90+ дней.
- Вкладки «Клиенты», «Счета», «Менеджеры», поиск, сортировка, выгрузка в CSV.
- Фильтр по филиалам. Филиал берётся из названия воронки сделки клиента в Битриксе (например, «Нур» и «Абая» это Алматы).
- Рядом с клиентом и счётом ссылка «сделка ↗», открывает последнюю сделку клиента в Битриксе.

**Роли и доступ**
- Админ: видит всё, управляет доступом, подключает вкладку в сделках. Выдать роль админа может любой админ.
- Видит всё: все данные, без управления доступом.
- Директор филиала: только данные своих филиалов.
- Менеджер: только свои клиенты (по ответственному в сделке).
- Список сотрудников и ролей меняется в самом приложении (кнопка «Доступ»), без перезапуска.

**Выставление счёта из сделки**
- Вкладка «Выставить счёт» в карточке сделки (в меню «Еще»).
- Клиент, услуга и сумма подставляются из сделки. Счёт создаётся в 1С «Мой арбитр» (контрагент и договор создаются, если их нет) и как смарт-счёт в Битриксе, привязанный к сделке. После создания счёт показывается на экране, его можно распечатать.
- Менеджер выставляет счета только по своим сделкам.

Чеки (фискализация) не входят: 1С:WebKassa в базе не настроена, а у Kaspi нет бесплатного API для чеков. См. раздел «Ограничения».

## Как это работает

```
Битрикс24 (iframe) ──AUTH_ID──▶ Node.js (Express) ──OData, Basic auth──▶ 1С Фреш (две базы)
                                   │
                                   └──REST, входящий вебхук──▶ Битрикс24 (воронки, сделки, смарт-счета)
```

- Пароль 1С и вебхук Битрикса живут только в `.env` на сервере, в браузер не попадают.
- Приложение открывается только из портала (`frame-ancestors`), пользователь проверяется запросом `user.current` к Битриксу, дальше выдаётся подписанная сессия (HMAC, 12 часов).
- База данных не нужна. В `data/` лежат `access.json` (доступы) и `branch-index.json` (кэш соответствия клиент – филиал, обновляется раз в час).

### Как считаются показатели

| Показатель | Источник |
|---|---|
| Счета | документ «Счет на оплату покупателю» за период |
| Начислено | проводки Дт 1210 / Кт не 1210 и не 3510 |
| Оплачено | проводки Кт 1210 или 3510 / Дт касса, банк, Kaspi |
| Долг | сальдо Дт 1210 по контрагенту (раздельное сальдо Дт/Кт) |
| Аванс | сальдо Кт 3510 и переплата по 1210 |
| Просрочка | долг раскладывается по FIFO на последние начисления; если начислению больше `PAYMENT_TERM_DAYS` дней, часть просрочена |

Деньги считаются по бухгалтерии (регистр «Типовой»), а не по статусам счетов, поэтому цифры сопоставимы с ОСВ по 1210. Определение «долга» может отличаться от виджета на главной странице 1С (там суммируются ещё 1274 и дебетовая часть 3510).

### Структура проекта

```
src/server.js      маршруты, сессии, права, выдача отчёта
src/config.js      .env и список компаний (CO1_* … CO9_*)
src/odata.js       клиент OData 1С (чтение и создание)
src/source1c.js    чтение счетов, остатков, проводок
src/sourceMock.js  тестовые данные для режима MOCK
src/report.js      расчёт долга, возраста долга, срез по правам
src/branches.js    филиалы из воронок Битрикса, индекс клиент – филиал
src/bitrixApi.js   вызовы REST Битрикса через вебхук (batch)
src/bitrix.js      проверка запуска из Битрикса, подписанные сессии
src/access.js      роли и список доступа (data/access.json)
src/invoicing.js   выставление счёта: 1С + смарт-счёт в Битриксе
public/            интерфейс отчёта и вкладки «Выставить счёт»
scripts/discover.js проверка связи с 1С и имён объектов
deploy/            примеры конфигов Caddy, nginx, systemd
```

## Установка

### 1. Подготовить 1С Фреш (для каждой базы)

1. Под администратором: **Администрирование → Синхронизация данных → Настройка стандартного интерфейса OData**.
2. Создать отдельного пользователя для OData с **длинным паролем** (его используют и для чтения, и для создания счетов).
3. В составе объектов отметить: план счетов «Типовой», регистр бухгалтерии «Типовой», документ «Счет на оплату покупателю», справочники «Контрагенты», «Пользователи», «Договоры контрагентов», «Номенклатура». Зависимости платформа подтянет сама.
4. Адрес OData: адрес базы из браузера + `/odata/standard.odata`.

### 2. Запустить сервис

Нужны Node.js 18+ (в Docker используется 22), домен и HTTPS.

```bash
git clone <репозиторий> && cd <папка>
cp .env.example .env     # заполнить: SESSION_SECRET, BITRIX_WEBHOOK, CO1_*, CO2_*
npm ci --omit=dev
npm run discover         # проверка связи с 1С; можно указать id компании
npm start
```

Через Docker:

```bash
docker compose up -d --build
```

`compose.yaml` рассчитан на внешнюю сеть `bashnya_default` с обратным прокси; при другой схеме уберите блок `networks` и пробросьте порт 3010. Примеры прокси в `deploy/` (Caddy, nginx). Важно не отдавать заголовок `X-Frame-Options: DENY`, иначе Битрикс не сможет показать приложение в iframe. Проверка: `curl https://ваш-домен/health`.

### 3. Вебхук Битрикса

**Разработчикам → Другое → Входящий вебхук**, права: `crm`, `user`, `department`. Ссылку записать в `BITRIX_WEBHOOK`.

### 4. Локальное приложение

**Разработчикам → Другое → Локальное приложение**

| Поле | Значение |
|---|---|
| Тип | Серверное |
| Путь обработчика | `https://ваш-домен/` |
| Путь первоначальной установки | `https://ваш-домен/install` |
| Приложение само завершает установку | включено |
| Название пункта меню | Дебиторка 1С |
| Права | `user_brief`, `placement`, `crm` |

### 5. Вкладка «Выставить счёт» в сделках

Откройте приложение под админом и нажмите **«Вкладка «Счёт» в сделках»**. Кнопка регистрирует вкладку `CRM_DEAL_DETAIL_TAB` (нужны права `placement` и `crm` у приложения). После этого вкладка появится в «Еще» карточки сделки.

## Настройки (.env)

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `PORT` | 3010 | порт сервиса |
| `SESSION_SECRET` | | длинная случайная строка для подписи сессий |
| `BITRIX_DOMAIN` | myarbitr.bitrix24.kz | единственный портал, которому разрешён запуск |
| `BITRIX_WEBHOOK` | | входящий вебхук (crm, user, department) |
| `CO1_ID`, `CO1_NAME`, `CO1_ODATA_URL`, `CO1_ODATA_USER`, `CO1_ODATA_PASSWORD` | | компания 1 (до `CO9_*`). Счета выставляются из компании с id `moy` |
| `CO2_ADMIN_ONLY` | 0 | 1 = компанию видят только администраторы приложения (так настроен АрбитрЪ) |
| `ACC_RECEIVABLE` | 1210 | счета дебиторки |
| `ACC_ADVANCES` | 3510 | счета авансов |
| `PAYMENT_TERM_DAYS` | 5 | срок оплаты, дней |
| `AGING_LOOKBACK_MONTHS` | 24 | глубина расчёта возраста долга |
| `CACHE_TTL_MIN` | 10 | кэш ответов 1С; кнопка «Обновить» сбрасывает |
| `MOCK` | 0 | 1 = тестовые данные без 1С |
| `DEV_NO_AUTH` | 0 | 1 = открывать без Битрикса (только локально) |

Без `CO1_*` приложение стартует в режиме `MOCK`. Для просмотра интерфейса: `npm run dev` и `http://localhost:3010`.

## Безопасность

- В репозиторий не попадают `.env` и `data/` (см. `.gitignore`). Пароль 1С и вебхук нельзя коммитить.
- Пользователь OData в 1С может создавать документы. Задайте ему длинный уникальный пароль и не используйте его в других местах.
- Доступ к отчёту проверяется на каждом запросе: убранный сотрудник теряет доступ сразу.
- Выставление счёта доступно ролям админ, директор и менеджер (только свои сделки); в журнале сервиса остаётся запись `[invoice] user=… deal=…`.
- Основной админ (ID 30833, константа `ROOT_ADMIN` в `src/access.js`) не может быть разжалован через интерфейс.

## Ограничения и идеи

- **Чеки.** 1С:WebKassa в базе не настроена. Kaspi Касса пробивает чек сама, когда клиент платит по счёту Kaspi Pay («Удалённая оплата»), но бесплатного API для создания счёта или чека у Kaspi нет. Рабочий бесплатный путь: счёт отправляется клиенту через Kaspi Pay вручную, оплата отмечается в сделке.
- Часть клиентов не получает филиал, если у них нет сделки с воронкой нужного филиала. Админ видит их в фильтре «Без филиала».
- Счёт создаётся непроведённым, как и прежние счета в базе. Проведение делает бухгалтер.
- Идеи: отметка оплаты в смарт-счёте по данным 1С, ежедневный отчёт по просрочке менеджерам, печатная форма счёта в PDF.
